Q: What lowers timing during an overrun fuel cut?

1. NO DECODED TERM GATED ON AN OVERRUN CUT BYTE HOLDS TIMING LOW THROUGH A COUNTED (PEDAL-LIFT) CUT in these
   calibrations.  That covers the DECODED consumers only: the reader scan is a lower bound and several readers
   are not decoded (c), so the general question stays OPEN (N5, N9).  The decoded timing-side consumers are:
   a. [8028], the overrun retard, which acts at the cut EXIT, not during it, and reaches the logged cell only on
      the sum path of 0x03F368 (point 2);
   b. neutral by calibration: the [8024] side of 0x041A7E (gate [802C] needs [6350] > 200.0 AND [63F8] < 0.0 AND
      x < 0.0; both mode tables are all zero; the mode-3 constant 0x0D2C28 is 0.0), the [7EEB] / [7EC4] cap of
      0x03F00C (set only with x >= 12000.0 and [63F8] >= 5.0 on the rising edge of the any-cut byte [7C68]) and
      the [80B4] term: 0x042ED8 drives [80B4] to 0.0 from any start on either branch of its [79C8] test (0.0 is
      a fixed point of both; its target table 0x0AE514 is all zero), so the cut byte is irrelevant to it.  (The
      cut byte does not even reach [79C8] in the same call: in 0x036322 [79C8] is 0 whenever word [79C4] == 0
      or [79F3] == 1, cut or not; [7C68] == 1 only skips the [79C0] update on the [79F3] == 1 branch.)
   c. not decoded past the first hop: 0x050A5A ([7C9D] -> [8910], point 4 candidate 2), the 0x01FE46 ->
      [641C] -> load path (candidate 3), the direct [7C68] readers 0x031A6A 0x034DA6 0x037B74 0x037CA0
      0x039868 0x03CD4A and the other callers of 0x03AB20, and 25 of the 32 [7C9D] readers.  (0x038E64, also a
      [7C68] reader, is decoded in fn_038E64_trace.txt; its sum S goes to 0x02FFE0, not traced to a timing
      input there.)
   d. at function level only able to turn the [7EC0] cap OFF (0x0312DE / 0x01FE46 -> 0x030F02 -> [73E8]), which
      cannot lower timing.
   The subtracted retard [7EC8] of 0x03F00C, which sits AFTER the sum's clamps, is not a cut term: its trigger
   r10/r11 is byte [7EED] (03F08A / 03F090, the load in the delay slot of the call to 0x03AB20), written by
   0x03EF58 from [6254], [7EEC] and x.  No cut byte reaches it.
   NOT cut-gated, but a live LOWERING bound the first decode did not evaluate: the [7EC0] cap LOAD (point 5).

   before 0x03F00C / 0x03F368:

     then  [8032] != 0 -> [8020] = 0.0;  [8033] != 0 -> [8020] = record 0x0ADE08([6350]);  both 0 -> ramp

     RESET [8020] = 0, counters 0, when ([65C5] != 1 and [5E94] < 4) or [6254] == 0 or [6634] < -20.0 or x < 0.0.
   0x0ADE08 on the ECT axis 0x0D2F8C (-40..110): 0 up to 0, -8.09 at 10, -11.95 at 20, -16.17 at 30, -17.93 at
   40, -20.04 at 50..60, -24.96 from 70.  The table value is written on EVERY armed call (the counters are
   reloaded in that same call) and the ramp starts on the first un-armed call after: 36 calls from -24.96 to 0.0

5. A LIVE LOWERING BOUND THAT IS NOT CUT-GATED: THE [7EC0] CAP LOAD.  In 0x03F00C a falling edge of byte
   [85D7] ([7F05] == 1 and [85D7] == 0) sets the latch r13 / [7F09].  While the latch is set, no OFF condition
   holds and [7EEA] == 1, [7EC0] := [7ECC] on EVERY call; a call with [7EEA] == 0 ramps [7EC0] by +0.7 but
   keeps the latch; only an OFF condition (any of [8F16] == 1, [85D7] == 1, [62FC] >= 120, [62F8] >= 60, the
   [805C] band test, [73E8] > 0) clears it.  [7ECC] is written by 0x03FA8C (69.65, init) and by 0x03ED56
   (caller 0x049BA4; listed below): [7ECC] = max([7ED0], 0x0ADAAC([6350])), where [7ED0] = 69.65 when
   [65C5] != 1 and word [5E74] >= word 0x0D29AE (38), else chosen by byte [6810]: 1 -> 0x0ADAC0(x) (-2.07 at
   x <= 1600 .. 8.13 at 3200), 2 -> 0x0ADAD4(x) (0.04 .. 8.13), 3 -> 0x0ADAE8(x) (4.96 at 1600, 28.16 from 2000),
   4 / 5 -> 10.0, other -> 69.7; 0x0ADAAC is 20.08 for [6350] <= 30 and -20.0 for [6350] >= 70, so there the
   cap is [7ED0].
   The clamp chain then caps the logged cell at [7EC0] (emulated: [7ECC] = -2.07 logs a sum of 30.0 as -2.07).
   Same bytes in the three bins.  Whether [7EEA] == 1, [6810] in 1..5, or ([65C5] == 1 or [5E74] < 38) ever
   hold on the car is NOT established (N10), and nothing here ties the mechanism to a cut.
