WHY THIS SLICE
--------------------------------------------------------------------------------
1,094 table descriptors decode cleanly from ROM bytes. Joining each descriptor's
DATA and AXIS pointers against every address the definition XMLs claim:

    descriptors whose data/axis IS defined in the XML :  308
    descriptors with NO definition anywhere          :  786   (775 plausible,
                                                               11 look like
                                                               scanner artefacts)

Of those 786, exactly 41 are 2-D on RPM x engine load -- the shape of every
real engine map, and therefore the highest-value slice to take first.

Join note: the definitions point at DATA, never at descriptor records. Joining on
the descriptor's own address returns zero matches and looks like "nothing is
defined". Join on the pointers inside the record.

RESULT
--------------------------------------------------------------------------------
14 of the 41 are FLAT (every cell identical) -- inert as shipped.
Subsystem split:

    (unassigned)               18
    DIAGNOSTIC MONITOR         11
    OL enrichment workspace    6
    CL fuelling target comp    3
    fuel/transient GBR         2
    FLKC workspace             1



READ THIS BEFORE TREATING ANY ROW AS A LEVER
--------------------------------------------------------------------------------
* "Subsystem" is a HINT, derived from RAM addresses referenced near the call
  site, and several of those RAM labels are themselves project guesses. It is
  not an identification. No table below is NAMED here.
* FLAT does not mean "safe to populate". `0xAD258` and `0xD2D48` are both flat
  and both feed multipliers that are separately clamped to zero -- populating
  them changes nothing. Read the consumer before acting.
* `0xABC1C` decodes to values spanning -1.3e5 .. 1.7e22. It is almost certainly
  a SCANNER ARTEFACT, not a table. 11 of the 786 look like this.
* The eight `0xAE6D4`/`0xAE724`-family rows are ALREADY IDENTIFIED --
  corrections item 82, the knock sigma multiplier and its threshold-B gain.
  They appear here because they carry no XML definition, which is itself the
  finding: the whole knock front-end is invisible to ECUFlash.
* `0xAD8D4` and `0xAD90C` are the CL Fuelling Target Compensation siblings that
  item 70 flagged as "live siblings missing from the XML". Confirmed here.

THE ONE CLUSTER WORTH A CLOSER LOOK
--------------------------------------------------------------------------------
`0xAD960` / `0xAD97C` / `0xAD998` / `0xAD9B4` / `0xAD9D0` all hang off one
function at `0x03684A`, whose GBR is `0xFFFF798C`. Its two lookup inputs are
read straight from RAM at the top:

  03685A: D26F  mov.l @(0x036A18),r2      ; [036A18] = FFFF6624   RPM
  03685C: FC28  fmov.s @r2,fr12
  03685E: D26F  mov.l @(0x036A1C),r2      ; [036A1C] = FFFF63F8   ENGINE LOAD
  036860: FF28  fmov.s @r2,fr15

It then folds the knock workspace in before the lookup:

  036874: F860  fadd fr6,fr8              ; [FFFF7F48] + [FFFF8258]
  036876: F891  fsub fr9,fr8              ; ... - [FFFF7E90]
  03687A: FD87  fmov.s fr8,@(r0,r13)      ; -> FFFF79B4

and picks between the two 15x12 surfaces on whether the GBR variable is non-zero:

  03687C: D26C  mov.l @(0x036A30),r2      ; [036A30] = 000BE608   outside-band test
  036886: 420B    jsr @r2
  036888: F4D6  fmov.s @(r0,r13),fr4      ; r0 = -108  -> FFFF798C
  03688E: 8909  bt 0x0368A4               ; in-band (== 0) -> 0xAD97C
  036890: D469  mov.l @(0x036A38),r4      ; else        -> 0xAD960

`0x0BE608` is the same outside-a-band-around-c helper decoded in item 83; here
c = 0.0 and eps = `[0x036A34]` = 3.0517578125e-05 (2^-15), i.e. the test is
simply "is `[0xFFFF798C]` non-zero".

Geometry of the cluster (all RPM 800-6400 x load 0.30-2.50 g/rev):

    0xAD960  uint16 15x12  scale 0.02288818  data  390.50 .. 866.25
    0xAD97C  uint16 15x12  scale 0.02288818  data  390.50 .. 1138.00
    0xAD998  uint16 13x12  scale 0.00390625  data    0.0195 .. 0.0742
    0xAD9B4  uint16 13x12  scale 0.00390625  data    0.0117 .. 0.1094
    0xAD9D0  uint16 13x12  scale 3.0518e-05  data    0.0100 flat

`0xFFFF798C` carries the project label `ol_enrichment_accum` and `0xFFFF8258` was
settled in item 80 as a knock-workspace integrator. Both are inputs here. That
makes this cluster knock-adjacent AND fuel-adjacent, which is exactly why it
should NOT be named from the label alone. `0xFFFF7F48` and `0xFFFF7E90` are
unidentified. **Structure established; meaning NOT established.**
