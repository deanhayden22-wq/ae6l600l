ANSWER
--------------------------------------------------------------------------------
`0xFFFF77D8` is the FIRST TERM of a two-term fuel trim whose partner is
`0xFFFF77DC`. It has **NO WRITER anywhere in the ROM**. The pair is consumed at
`0x03961C` (reached only from `func_3952C`) as:

    S = 1.0 + [0xFFFF77D8] + [0xFFFF77DC]
    if |S - 0.0| <= 0.0001220703125:   [0xFFFF7BAC] = 0.0
    else:                              [0xFFFF7BAC] = clamp(1.0/S - 1.0, 0.0, 0.03)

The 0.03 ceiling is float `[0x0CC3E8]`. So the output is a **positive fuel trim
capped at +3%**, and with `[0xFFFF77D8]` contributing nothing the trim is driven
entirely by `[0xFFFF77DC]`.

WRITER SEARCH -- four independent methods, all negative
--------------------------------------------------------------------------------
1. `scripts/mapping/find_writers.py FFFF77D8` -> "no writes found".

2. Exhaustive literal enumeration. The 32-bit value `FFFF77D8` occurs at exactly
   FOUR aligned offsets in the 1 MB image:

       0x032450   literal pool  -> loaded at 0x032260, READ
       0x03972C   literal pool  -> loaded at 0x03953A, READ
       0x07D788   literal pool  -> loaded at 0x07D680, READ
       0x063A34   pointer-table slot -- see (4)

   Every PC-relative `mov.l @(disp,pc),rN` in the image resolving to any of the
   three pool addresses was enumerated. There are exactly three, all reads.

3. Store-base back-trace over 0x000000-0x0C0000 for `fmov.s frM,@rN`,
   `fmov.s frM,@-rN` and `mov.l rM,@rN`, resolving rN through literal loads,
   `mov rM,rN`, `mov.l @rM,rN`, `mov.l @(disp,rM),rN` and accumulated
   `add #imm,rN`: ZERO stores resolve to `0xFFFF77D8`.

4. GBR enumeration. All 651 `ldc rN,gbr` sites were resolved to their literal
   bases. Three bases can reach `0xFFFF77D8` with a legal displacement
   (`FFFF77BC`+7, `FFFF77C8`+4, `FFFF7710`+50). Every matching `mov.l r0,@(d,gbr)`
   in the image lies far outside the function where that base is live -- these
   are data decoded as code, the phantom class of corrections item 73. Note also
   that all three READS are `fmov.s` (float); SH-2E has no GBR-relative float
   store, so a GBR write would have to be an integer store of a float bit
   pattern.

THE POINTER-TABLE SLOT IS UNREACHABLE
--------------------------------------------------------------------------------
`0x063A34` sits in a table of RAM pointers:

    063A2C  FFFF77C8      063A38  FFFF77E4      063A44  FFFF77DC
    063A30  FFFF77CC      063A3C  FFFF782A      063A48  FFFF77E0
    063A34  FFFF77D8  <-- 063A40  FFFF7864

`0xFFFF77DC`'s writer works by being HANDED its slot address: `0x03342E` loads
`0x00063A44` from a literal, `0x033342 bsr 0x033CC0` passes it in r4, and the
helper dereferences and stores. That is the idiom, and it is why a literal-pool
scan alone settles nothing (open-holes' own warning).

But **no literal anywhere in the image holds `0x00063A34`**, `0x00063A30` or
`0x00063A38`. The only slots ever passed are `0x639C4`, `0x63A04`, `0x63A10`,
`0x63A2C`, `0x63A3C`, `0x63A44`, `0x63A48`. And the two helpers that receive a
neighbouring slot index past `0x63A34`, not onto it:

    0x033658  r11 = r5 = 0x63A2C ; mov.l @(4,r11),r2   -> 0x63A30 = FFFF77CC
              r10 = r4 = 0x63A3C ; mov.l @(4,r10),r6   -> 0x63A40 = FFFF7864
    0x033D1C  r13 = r5 = 0x63A2C ; mov.l @(12,r13),r2  -> 0x63A38 = FFFF77E4

Each of the six helpers called from `0x03333C`-`0x033358` has exactly ONE caller
(verified by scanning every `bsr` displacement in the image). So the slot holding
`0xFFFF77D8` is reachable from no code path.

`0xFFFF77D8` lies inside `FFFF4000..FFFFBF9F`, the fourth entry of the RAM region
table at `0x011CCC`-`0x011CE8` (`FFFF0000-001F`, `0020-1FFF`, `2000-3FFF`,
`4000-BF9F`). Whether that table drives a startup clear is NOT established here.

WHAT THIS MEANS NUMERICALLY
--------------------------------------------------------------------------------
`0xFFFF77DC` is written from the four CL Fueling Target Compensation tables via
descriptors `0xAD8B8` / `0xAD8D4` / `0xAD8F0` / `0xAD90C` (corrections item 70).
Re-read 2026-08-19 with `desc_types.read_table`:

    0AD8B8  2D uint16  n=110  -0.14999 .. -0.00800
    0AD8D4  2D uint16  n=110  -0.14999 .. -0.00800
    0AD8F0  2D uint16  n=156  -0.14999 .. -0.00475
    0AD90C  2D uint16  n=156  -0.14999 .. -0.00475
    TOTAL   n=532            -0.14999 .. -0.00475   (all negative)

With `[77D8] = 0`, `S = 1 + [77DC]` lies in `[0.85001, 0.99525]`, so
`1/S - 1` lies in `[0.00477, 0.17646]` -- ALWAYS POSITIVE, never near the
guard's zero band. Therefore:

* The `[0xFFFF7BAC] = 0.0` path is UNREACHABLE for any value these tables can
  produce. It would need `[77D8] + [77DC]` near -1.0.
* The trim SATURATES at the +3% ceiling whenever `[77DC] <= -0.029126`.
  That is **56 of 532 cells (10.5%)**. The other 89.5% give a graded
  +0.48% .. +3% enrichment.

CORRECTIONS to the previous open-holes entry
--------------------------------------------------------------------------------
* "It is suppressed only when `[0xFFFF77D8] >= +0.00475...+0.150`" -- WRONG.
  The suppression test is `|1 + [77D8] + [77DC]| <= 1.22e-4`, i.e. the sum near
  -1.0. The `0.00475..0.150` figures are the MAGNITUDES of the 77DC table data,
  not a threshold on 77D8.
* "Branch A of `func_3952C` arms by default, not as an edge case" -- right
  conclusion, wrong reason. It arms because the guard is a divide-by-zero check
  that essentially never trips, not because of a comparison against 77D8.
* The suggested next move (`map_gbr_structures.py` / `identify_gbr_workspaces.py`
  to find what loads R9 in the AFC PI controller) does not apply: the
  `afc_pi_controller_trace.txt:191` "R9+0xB0" reading is not corroborated by any
  store this trace can find, and R9-relative float stores in that region resolve
  elsewhere.

STILL OPEN
--------------------------------------------------------------------------------
* Whether `0xFFFF77D8` is explicitly zeroed at reset or merely never written.
  The RAM region table at `0x011CCC` covers it, but the consumer of that table
  was not decoded. Either way the read value is a constant for a given power
  cycle, and every method above agrees nothing in the ROM changes it.
* `0xFFFF7BAC`'s own consumers are not traced here.
* None of `0x0CC3E8` (0.03), `0x0CC3EC` (0.0), `0x0CC3F0` (0.0), `0xAD8B8`,
  `0xAD8D4`, `0xAD8F0`, `0xAD90C` has an `address=` entry in the project XML
  (checked 2026-08-19). `0x0D1600` and `0x0D18DC` remain live siblings missing
  from the XML, per item 70.
