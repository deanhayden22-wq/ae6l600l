PART 0 -- THE UNITS. This is the whole answer to "why is FFB below the map".
--------------------------------------------------------------------------------
VERIFIED. Primary Open Loop Fueling uses scaling EstimatedAir/FuelRatio
(32BITBASE.xml:67):

    toexpr = 14.7/(1 + x*.0078125)

The map does NOT store an AFR. It stores (phi - 1) * 128, an ENRICHMENT OVER
STOICH, where phi = 14.7/AFR is the equivalence ratio.

The logged FFB channel is the same quantity:

    logs/logcfg.txt:14   paramid 0xFF6852, databits 16
    scalingrpn = 14.7,x,.0004882812,*,/      ->  AFR = 14.7 / (raw/2048)

So FFB and the OL map are the SAME quantity in the SAME units, and the map is
ONE ADDEND in a sum. FFB reads below the map (in AFR) whenever any other term is
positive. Nothing is lost, and no hidden multiplier is involved.

Consequence worth carrying: the terms add in phi, and you read the result in
AFR. The AFR gap is therefore NOT constant. The same +0.105 of enrichment is
~0.8 AFR at an 11.0 command but only ~0.15 AFR at 14.7. A gap that looks
dramatic at WOT can be an ordinary constant term.

Worked example (the numbers from the 2026-08-16 brief):
    map  11.0 AFR -> phi = 1.3364
    FFB  10.2 AFR -> phi = 1.4412
    delta phi = 0.1048  =  13.4 counts on the map's own 128-per-unit scale.

--------------------------------------------------------------------------------
PART 1 -- THE LOGGING PATH (how the number reaches the datalogger)
--------------------------------------------------------------------------------
VERIFIED.

  1. FFB paramid 0xFF6852 -> RAM 0xFFFF6852.
  2. 0xFFFF6852 has exactly ONE writer, GBR-relative (a literal-pool scan finds
     zero, which is why this needed find_writers.py):

        0244FC: C10B  mov.w r0,@(22,gbr)      ; GBR = 0xFFFF683C set @0243C8
                                              ; 0xFFFF683C + 22 = 0xFFFF6852

  3. It sits in the SSM packing block. The source and scale are the three
     instructions before it:

        0244EE: D277  mov.l @(0x0246CC),r2    ; r2  = 0xFFFF730C   <- SOURCE
        0244F0: F428  fmov.s @r2,fr4
        0244F2: F6DC  fmov fr13,fr6           ; fr6 = 0.0  (bias, fldi0 @0243D0)
        0244F4: C776  mova @(0x0246D0),r0
        0244F6: FF08  fmov.s @r0,fr15         ; fr15 = 0.000488281 = 1/2048
        0244F8: 4D0B  jsr @r13                ; r13 = 0x000BE5D8
        0244FA: F5FC  fmov fr15,fr5           ; fr5 = scale

  4. The packer 0x0BE5D8 is round-then-clamp:

        0BE5DA  fsub fr6,fr4        ; v - bias
        0BE5DE  fdiv fr5,fr4        ; / scale
        0BE5E0..E6  fadd 0.5 ; ftrc ; clamp to [0, 0xFFFF]
                              (0.5 at 0x0BE600, 0xFFFF at 0x0BE604)

     => stored word = round(phi * 2048), which the logcfg expression inverts.

  ** 0xFFFF730C IS THE COMMANDED EQUIVALENCE RATIO phi. **

  Note: 0xFFFF730C is the COMMON (pre-per-cylinder) command. The four
  per-cylinder values are stored separately at -48/-44/-40/-36 off 0xFFFF7340
  (0x030128 onward) and are NOT in FFB.

--------------------------------------------------------------------------------
PART 2 -- WHERE 0xFFFF730C COMES FROM
--------------------------------------------------------------------------------
VERIFIED. One writer, indexed:

    03011C: FD07  fmov.s fr0,@(r0,r13)   ; r13 = 0xFFFF7340, r0 = -52
                                         ; 0xFFFF7340 - 52 = 0xFFFF730C

fr0 is the output of the clamp helper 0x0BE56C called at 0x030116 with
fr5 = 0.0 (lo) and fr6 = 32.0 (hi):

    030110  mova @(0x0301E0),r0 / fmov.s @r0,fr14   ; 32.0
    030116  jsr @r14 (=0x0BE56C) / 030118 fldi0 fr5

and its input fr4 is set at 0x0300BE-0x0300C4:

    0300BE: F4EC  fmov fr14,fr4          ; fr4 = the accumulated sum
    0300C0: DD28  mov.l @(0x030164),r13  ; r13 = 0xFFFF7340
    0300C2: F8D8  fmov.s @r13,fr8
    0300C4: F482  fmul fr8,fr4           ; fr4 = sum * [0xFFFF7340]

    FFB_phi = clamp( SUM * [0xFFFF7340], 0.0, 32.0 )

[0xFFFF7340] is 1.0 in normal running -- VERIFIED at its three writers:
    02FF74 fldi1 fr8 / 02FF7A fmov.s fr8,@r2        -> 1.0
    02FFD4 fldi1 fr5 / 02FFD8 fmov.s fr5,@r2        -> 1.0
    02FFCE/02FFD2                                   -> clamp(1 + byte/100, hi 1.2)
The 1.2 path is reached ONLY when byte[0xFFFF8F24]==1 AND byte[0xFFFF8F08]!=0
(02FFA4-02FFB2). Treat it as a special mode, not a normal-driving term.

--------------------------------------------------------------------------------
PART 3 -- THE SUM, TERM BY TERM  (function 0x02FFE0-0x03012E)
--------------------------------------------------------------------------------
VERIFIED structure. There are TWO structurally different summations, selected by
a ROM CAL BYTE:

    030070  mov.b @r6,r0   ; r6 = 0x0CBBD2
    030072  cmp/eq #90,r0
    030074  bf/s 0x030096

    ROM byte [0x0CBBD2] = 0x00 on this cal  ->  NOT-EQUAL branch is LIVE.
    The ==90 branch (0x030078-0x030094) is DEAD on this calibration.

LIVE FORMULA (branch 0x030096, assembled from 0x03003A-0x0300BC):

    base    = 1.0 + [73B4] + [7A08] + [7A14] + [7AF4] + [7B8C]
    floor   = MIN( [73A4] + [7BE4], 0.65 ) + [7354] + [7374]
    mapterm = MIN( [798C] + [7A20], 0.52 )
    phi     = base + MAX( mapterm, floor ) - [7A44] + [7BCC] + [7BA8]

  (all addresses 0xFFFFxxxx; helpers VERIFIED from bytes this session:
   0x0BE960 = MAX -- 0BE960 fcmp/gt fr5,fr4 -> returns fr4 if fr4>fr5
   0x0BE970 = MIN -- 0BE970 fcmp/gt fr4,fr5 -> returns fr4 if fr5>fr4
   This confirms CLAUDE.md and corrects a reversed one-line note in the
   project memory index.)

The MAX(mapterm, floor) is the classic "minimum enrichment" structure: whichever
of the OL map path and the minimum-enrichment path is RICHER wins.

--------------------------------------------------------------------------------
PART 5 -- THE RICH CLAMPS (the two most consequential numbers here)
--------------------------------------------------------------------------------
VERIFIED values, INFERRED interpretation:

    0x0CBE04 = 0.52   caps the OL-map path      -> phi 1.52 -> 9.67 AFR
    0x0CBE00 = 0.65   caps the floor path       -> phi 1.65 -> 8.91 AFR

Both are hard MIN clamps applied BEFORE the MAX, so they bound how rich each
path can ask for on its own. Neither has an XML definition.

--------------------------------------------------------------------------------
PART 6 -- WHAT THIS CLOSES
--------------------------------------------------------------------------------
The 2026-08-16 brief framed "FFB ~0.8 AFR below the OL map at WOT" as evidence
of a missing MULTIPLIER in the IPW stack, and item 42 removed 0xAD258 as that
lever without replacing the frame. The frame itself was wrong: the command is a
SUM in phi-space, not a product in AFR-space, and the map is one addend of about
a dozen. The gap needs no unexplained multiplier.
