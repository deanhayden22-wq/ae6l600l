ARGUMENT ORDER -- THE THING MOST LIKELY TO BE GOT WRONG BY A CALLER'S READER
  The two integer->float routines take   raw = r4, SCALE = fr4, OFFSET = fr5.
  The two float->integer routines take   x = fr4,  SCALE = fr5, OFFSET = fr6.
  The scale and offset sit one register higher on the way back.  0x0BE5A8/0x0BE5D8 are the algebraic
  inverses of 0x0BE588/0x0BE598 only if the caller shifts them accordingly.
  The clamp takes (x, LOW, HIGH) = (fr4, fr5, fr6); the window test takes (x, CENTRE, HALF-WIDTH); the
  hysteresis comparator takes (x, THRESHOLD, WIDTH) plus the previous state in r4.

      of the result.  On the script's grids the two truncating models are up to 80 float32 steps apart for
      0x0BE588 (raw 71, scale 1.8, offset -128: -0.200003386 against -0.200004578) and up to 509 for

  CONSEQUENCE FOR THIS FILE
  Operand roles, operation order, compare sense, saturation bounds and every special-case branch are
  established and do not depend on rounding.  0x0BE56C moves bits and never rounds; it is exact.  For the
  other six float routines every emulated result is asserted BIT-EXACT against the truncating model (each
  operation exact, then truncated once; fmac fused) -- the arithmetic the firmware expects, as far as the
  bytes reach (fused-vs-unfused is N1, inexact fadd/fsub is N2).  A ROUND-TO-NEAREST model -- the emulator
  before corrections item 106, or plain Python float arithmetic -- would give a different answer:
      0x0BE588 / 0x0BE598   in the low bits of fr0 whenever fr4 * raw + fr5 is inexact
      0x0BE628              in the last ulp of the quotient (and +Inf where truncation saturates at FLT_MAX)
      0x0BE5A8 / 0x0BE5D8   by one count, only when (x - offset) / scale + 0.5 lands on a rounding edge
      0x0BE608 / 0x0BE800   in the 0/1 verdict, only when x is within one float32 step of a computed limit
  How often that happens depends entirely on how close the inputs sit to an edge.  The script counts it on
  two different grids per routine precisely to show that the count is a property of the grid, not a rate
  (each is "round-to-nearest differs from the asserted truncation"; these are the same disagreements the
  old emulator showed against the truncating model, seen from the other side):

;     0x0BE588    10,926 of 32,256 results differ (a fused nearest fmac; 10,978 for an unfused one)
;     0x0BE598    6,072 of 16,758 (fused nearest; 6,070 unfused)
  The old emulator was not exactly "fused" either: in 28 of 32,256 cases (all at scale 3e33) it formed the
  sum in double first and rounded twice.  This file once quoted the old emulator against truncated-fused /
  truncated-unfused: 10,898 / 11,859 for 0x0BE588 (the 28 double-rounded cases are why the first is not

==== FUNCTION 0x0BE4FA .. 0x0BE522  (20 instructions, 2 calling functions) ====

CONTRACT
  inputs   r4  = address of a 12-byte record:  +0  int16 count (read with mov.w, so SIGN-extended)
                                                +2  2 bytes, never read
                                                +4  pointer to float32 thresholds[count]
                                                +8  pointer to uint8 values[count]
           fr4 = x (float32)
  output   r0  = one byte of values[], ZERO-extended to 32 bits (also left in r4)
  effects  none on memory.  Changes r0 r2 r4 r5 r6 r7 and fr8.  fr4 is preserved.

MECHANISM
  r4 = (u8) values[0]                      ; read unconditionally, before the count is looked at
  i  = count
  loop:
      i = i - 1
      if i < 0:           return r4        ; cmp/pz r5 sets T when r5 >= 0; bf leaves when T = 0
      if thresholds[i] > x:  goto loop     ; fcmp/gt fr4,fr8 sets T when fr8 > fr4 (fr8 = thresholds[i]); bt loops when T = 1
      r4 = (u8) values[i]
      return r4

  In words: scan the thresholds from the LAST entry down and return the value paired with the first threshold
  that is NOT greater than x (i.e. threshold <= x for ordered floats).  If every threshold is greater than x
  the result is values[0] -- the same answer as for thresholds[0] <= x < thresholds[1], so the bottom is
  clamped.  x >= thresholds[count-1] returns values[count-1].  Equality selects the higher bin (x equal to a
  threshold returns that threshold's value).
  Edges: count 1 always returns values[0].  count <= 0 (0, or 0x8000..0xFFFF read as negative) skips the loop
  and still returns values[0], which is still read.  Thresholds are not required to be sorted; with unsorted
  thresholds the highest index that passes wins.  There is no interpolation and no bounds check.
  x = NaN (EMU-MODEL: an unordered fcmp/gt leaves T = 0): the very first compare, at i = count-1, is "not
  greater", so the scan ends there and the TOP value comes back -- 15 on record 0x0AC2B0, 12 on 0x0AB328.
  A NaN selects the top bin, not the bottom one.

EVIDENCE

==== FUNCTION 0x0BE608 .. 0x0BE626  (15 instructions, 104 calling functions) ====

CONTRACT
  inputs   fr4 = x, fr5 = CENTRE, fr6 = HALF-WIDTH
  output   r0 = 1 when x < (fr5 - fr6) or x > (fr5 + fr6);  r0 = 0 otherwise      (also left in r4)
  effects  none on memory.  Changes r0, r4 and fr3.  fr4, fr5, fr6 are preserved.

MECHANISM
  fr3 = fr5 - fr6
  if fr3 > fr4:  return 1              ; fcmp/gt fr4,fr3 sets T when fr3 > fr4, i.e. x below the window
  fr3 = fr5 + fr6
  if fr4 > fr3:  return 1              ; fcmp/gt fr3,fr4 sets T when fr4 > fr3, i.e. x above the window
  return 0

  1 means OUTSIDE.  Both edges belong to the window: x == centre - width and x == centre + width return 0.
  Zero width: 0 only when x == centre exactly (all 1,352 grid cases).
  NEGATIVE width: the two limits cross, and the result is 1 for every x -- with truncating fsub/fadd, which
  the emulator implements since corrections item 106 (asserted: all 5,408 negative-width grid cases and
  the six negative-width rows of t_window return 1).  Under ROUND-TO-NEAREST -- the emulator before item
  106 -- it fails when the width is so small that centre - width and centre + width both round back to
  centre; then x == centre returns 0:
      round-to-nearest:  x = c = 10, w = -1e-30    -> 0      x = c = 10, w = -4.7e-7  -> 0   (below half an ulp of 10)
                         x = c = 10, w = -4.8e-7   -> 1      x = c = 10, w = -1       -> 1
                         x = c = 1e30, w = -65536  -> 0      (the width only has to be small against the centre)
  The round-to-nearest model returns 0 in 44 of the 5,408 negative-width grid cases, every one with
  x == centre (22 with w = -1e-30, the other 22 with the centre at +-1e30 or +-FLT_MAX).  This edge is a
  ROUNDING-MODE artefact, not a property of the bytes: a truncated centre -/+ width cannot land back on the
  centre from the side nearer zero, so one limit stays strictly beyond x and the result is 1.  So
  "negative width means always outside" is what the firmware's expected arithmetic gives -- given that
  fadd/fsub truncate too (N2; the self-test proves truncation only for fmul/fmac/fdiv).
  It is |x - centre| > width computed as two one-sided tests, not with fabs.

  0BE61E/0BE620  the 0 and the 1

==== FUNCTION 0x0BE654 .. 0x0BE7F8  (210 instructions, 3 calling functions) ====

CONTRACT
  inputs   r4 = dividend, r5 = divisor, both SIGNED 32-bit
  output   r0 = (r4 * 65536) / r5 as a signed 32-bit value, truncated toward zero, with saturation:
                 r4 == 0                               -> 0            (even when r5 == 0)
                 r5 == 0, r4 > 0                       -> 0x7FFFFFFF
                 r5 == 0, r4 < 0                       -> 0x80000000
                 r4 == 0x80000000 and r5 == -1         -> 0x7FFFFFFF
                 trunc(r4 / r5) >  32767               -> 0x7FFFFFFF
                 trunc(r4 / r5) < -32768               -> 0x80000000
                 otherwise                             -> low 32 bits of trunc((r4 << 16) / r5)
           i.e. the quotient r4/r5 in 16.16 fixed point (0x00010000 = 1.0).
  effects  none on memory, no stack use, MACH/MACL untouched (it is div0s/div1, not a multiply).
           Changes r0 r1 r3 r4 r6 r7 and the Q/M/T bits.  r5 is preserved.

MECHANISM
  if r4 == 0: return 0
  if r5 == 0: return 0x7FFFFFFF + (r4 < 0)             ; rotcl r4 puts the sign of r4 in T, addc adds it
  if (r4 & 0x7FFFFFFF) == 0 and r5 == -1: return 0x7FFFFFFF        ; r4 is 0x80000000 here (zero already excluded)
  r7 = r4
  -- division 1: r6 = trunc(r4 / r5), the classic 64/32 signed sequence
     r3:r4 = sign-extended dividend, minus 1 if negative (subc), div0s, 32 x (rotcl r4 ; div1 r5,r3),
     final rotcl, addc -> r6
  if r6 >  0x7FFF: return 0x7FFFFFFF                   ; cmp/gt r1,r6 sets T when r6 > r1 (signed), r1 = 0x00007FFF
  if r6 < -0x8000: return 0x80000000                   ; cmp/gt r6,r1 sets T when r1 > r6, r1 = 0xFFFF8000; r0 = ~0x7FFFFFFF
  -- division 2: r3:r7 = sign-extended original dividend shifted left 16 (16 x shal r7 ; rotcl r3)
     same adjust, div0s, 32 x (rotcl r7 ; div1 r5,r3), final rotcl, addc -> r0
  return r0

  THE GUARD HAS A HOLE.  It tests the INTEGER quotient against -32768, but the 16.16 result only fits when
  the true ratio is >= -32768.0.  When trunc(r4/r5) == -32768 and the division has a remainder (true ratio
  strictly between -32769 and -32768) division 2 overflows and the routine returns the low 32 bits of the
  true quotient -- a large POSITIVE number instead of 0x80000000.
      r4 = -98304, r5 = 3  (exactly -32768)   -> 0x80000000    correct
      r4 = -98305, r5 = 3  (-32768.33)        -> 0x7FFFAAAB    WRONG SIGN
      r4 = -98306, r5 = 3  (-32768.67)        -> 0x7FFF5556    WRONG SIGN
      r4 = -98307, r5 = 3  (-32769)           -> 0x80000000    saturated
      r4 =  65537, r5 = -2 (-32768.5)         -> 0x7FFF8000    WRONG SIGN
  The positive side has no such hole (ratio < 32768 always fits).  Whether any of the three callers can
  present such a ratio: NOT ESTABLISHED.

  Rounding is toward zero for both signs: 1/3 -> 0x00005555, -1/3 -> 0xFFFFAAAB (-21845), -3/2 -> 0xFFFE8000.

==== FUNCTION 0x0BE800 .. 0x0BE81C  (14 instructions, 11 calling functions) ====

CONTRACT
  inputs   fr4 = x, fr5 = THRESHOLD, fr6 = HYSTERESIS width, r4 = previous state (any 32-bit value)
  output   r0 = 1    when NOT (fr5 > fr4)            -- x at or above the threshold
                0    when (fr5 - fr6) > fr4          -- x below threshold minus width
                r4   otherwise, returned unchanged and unmasked
           (also left in r5)
  effects  none on memory.  Changes r0, r5, and fr5 (overwritten with fr5 - fr6 whenever x < threshold).
           r4, fr4 and fr6 are preserved.

MECHANISM
  if NOT (fr5 > fr4):  return 1        ; fcmp/gt fr4,fr5 sets T when fr5 > fr4; bt/s goes on when T = 1
  fr5 = fr5 - fr6
  if fr5 > fr4:        return 0        ; fcmp/gt fr4,fr5 again; bf/s takes the pass-through when T = 0
  return r4

  Sets at x >= threshold (equality sets).  Clears only at x < threshold - width (equality holds the old
  state).  In between the previous state comes straight back, all 32 bits of it.
  Zero or NEGATIVE width: the dead band is empty or inverted, so x < threshold gives 0 (for a negative width
  threshold - width is above the threshold, and the first test has already claimed x >= threshold).
  The rising edge is at the threshold itself; the width is applied on the falling side only.

EVIDENCE
  0BE800/0BE802  set test and branch sense
  0BE80A-0BE80E  clear test and branch sense (bf/s: taken when T = 0, into the pass-through at 0BE816)
  0BE816         mov r4,r5: the previous state is copied, not tested or masked
  emulated: t_hyst + t_edges, 36,749 cases (26^3 grid x previous-state 0xDEADBEEF and 0, 16 asserted rows
            incl. the four edges of the 0x046A68 call, 1 NaN row, 1,580 edge-targeted cases).  The emulator
            is exact with the fsub TRUNCATED (asserted); a round-to-nearest model differs in 34 of the 35,152
            grid verdicts and 40 of the 1,580 edge cases (x within one float32 step of threshold - width; grid
            counts, not rates).  The set edge (x >= threshold) involves no arithmetic and no rounding.
            EMU-MODEL: x = NaN returns 1 (the first fcmp/gt is false, which is the "set" arm).
