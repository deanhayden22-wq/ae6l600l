ANSWER
--------------------------------------------------------------------------------
Item 63 established that the "fuel dispatch tables" are literal pools and that
NOTHING walks the unrolled call runs. That still holds. What was left open --
"what calls the enclosing functions" -- has an answer, and there IS a walker,
just not where the original question looked:

    ISR stub (0x00E970 family)
      -> 0x00E774          raise SR to IMASK=15, pass r4 = event id
      -> 0x00010800        wrap the (id, payload) pair
      -> 0x00010B2A        <-- THE WALKER: linear scan of a 5-slot event table
      -> ... later ...
         task stubs at 0x00E4xx  -> 0x04A94C / 0x04AA58 / 0x049A7A /
                                    0x049BA4 / 0x049CF0 / ...
         each a straight-line run of `mov.l @(lit,pc),r2 / jsr @r2`

THE EVENT TABLE -- 5 slots, 12-byte stride, coalescing, silent drop
--------------------------------------------------------------------------------
    count  : byte  @ 0xFFFF2060
    entries: array @ 0xFFFF2064, STRIDE 12

    entry +0  word  event id
    entry +4  long  payload (the r5 passed in)
    entry +8  byte  pending counter, SATURATES at 255

    last posted id      -> word @ 0xFFFF20A0
    last posted payload -> long @ 0xFFFF20A4

Algorithm of 0x010B2A, read straight off the bytes below:

    n = count[FFFF2060]
    for i in 0 .. n-1:
        if entry[i].id == target:
            if entry[i].pending < 255: entry[i].pending += 1
            found = 1; break
    if not found and n < 5:
        entry[n].id      = target
        entry[n].payload = r5
        entry[n].pending = 1
        count[FFFF2060]  = n + 1
    [FFFF20A0] = target ; [FFFF20A4] = payload

Two consequences that are worth carrying:

* **Coalescing.** A repeat of an already-queued id does NOT take a second slot;
  it bumps that slot's counter. The counter is what tells the consumer how many
  times the event fired.
* **Silent drop.** A NEW event id arriving while count >= 5 is discarded. There
  is no error path, no overflow flag, no else branch -- control simply falls to
  the tail at 0x010BFC.

    r8 = r9 = count via 0x0BDA70(r4 = 0xFFFF2060)
    r12 = r13 = r14 = 0xFFFF2064          ; three cursors over the same array
    loop while r9 > 0:
        r0 = id at cursor via 0x0BDAAC(r4 = r14)   ; helper does mov.w @r14,r2

The 0x00FF at 0x010B92 is the saturation ceiling. `cmp/ge r3,r0` with r0 = the
counter and r3 = 255 skips the increment once it is pegged.

`cmp/ge r2,r9` sets T when r9 (the count) >= r2 (5). The `bt/s` therefore takes
the SKIP on a full queue -- the new event is dropped.

* `0x04AD40 "task_table"` -- it is a LITERAL POOL. The longs there are

`0x00E5EC-0x00E6C0` is 54 longs, every one a ROM code address, bounded by an

STILL OPEN
--------------------------------------------------------------------------------
* What DRAINS the event table -- the consumer that reads the pending counters
  and runs the corresponding task stub -- is not traced here. `0xFFFF2060` /
  `0xFFFF2064` are the addresses to start from.
* The accessor helpers `0x0BDA70` / `0x0BDAAC` / `0x0BDB6E` / `0x0BDB80` all open
  with `jsr 0x0000317C ; r4 = 16`. That common prologue is not decoded; it looks
  like a guarded-RAM access layer, but that is an inference, not a finding.
* Event ids seen in the ISR stubs decoded here: 80, 84, 90, 92. The full id map
  was not enumerated.
* `byte[0xFFFF8EDC]` (`sched_disable_flag`) has its readers here; its WRITER was
  not chased.
