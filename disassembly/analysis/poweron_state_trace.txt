Displacements are already in bytes.  "Reset" below means a pass through the power-on / manual-reset vector
0x000C0C.  "Cold" and "warm" are used in this ROM's own sense (0x010124): warm = word 0xFFFF2000 == 0xAA55 at
the time task 10 runs; the reset path itself never reads that word (emu pass C: identical instruction set).
"ITI" = the WDT interval-timer interrupt.  "Acceptance window" = from 0x00FA84 (after 0x00FA82 lowers SR.I to

ANSWER
  1. On EVERY reset, warm or cold, 0xFFFF4000..0xFFFFBF9F is all zero when the kernel starts.  0x010290 (called
     once, from 0x00FA86) first pattern-tests that range destructively, then 0x010398 programs DMAC channel 0
     with SAR = DAR = 0xFFFF4000, DMATCR = 0x1FE8, CHCR = 0x001F0128 after storing a zero long at 0xFFFF4000.
     By the manual's CHCR table that is auto-request (RS 11111), source FIXED (SM 00), destination INCREMENTED
     (DM 01), LONGWORD units (TS 10), burst (TM 1): 0x1FE8 copies of the zero long to 0xFFFF4000,
     0xFFFF4004, .., 0xFFFFBF9C.  The CPU spins on TE.  The fill runs on both outcomes of the RAM test (the
     failure branch 0x0102B6 goes straight to it) and does not depend on any marker.  After it, only two bytes
     in the range are written before the kernel start: 0xFFFF5B89 := RAM-test result bits (0 when all pass)
     and 0xFFFF5B6C := 0.  This holds with or without WDT interrupts: the ITI handler, when it returns, writes
     only long 0xFFFF0004 and its own stack frame, and frames pushed into the range while SP sits at
     0xFFFFBF9C (range-C test) are erased by the later fill (pass G).
  2. The reset path runs a BOOT WATCHDOG on the WDT interval-timer interrupt.  0x010878 (via 0x0108DA) sets
     long 0xFFFF0000 := 183 (limit), long 0xFFFF0004 := 0 (count), byte 0xFFFF0008 := 0.  0x00AE50 sets IPRL
     bits 7-4 (the WDT ITI priority, manual Table 7.4) to 14, 0x010942 sets TCSR TME (TCSR 0x3C: interval
     mode, CKS 4), and 0x00FA82 lowers SR.I to 13, so from 0x00FA84 on every WDT overflow requests an ITI that
     is taken outside the 0xE0 critical sections (a request raised inside one waits for its end; overflows
     while OVF is still set are not counted separately).  Vector 224 (VBR 0x000FFC50 + 0x380 = 0x0FFFD0 -> 0x00F6E6)
     saves r0-r7, fr0-fr11, pr, fpul, fpscr, clears OVF and calls 0x010AD8: count += 1; count < limit ->
     0x011880 (toggles bit 15 of port word 0xFFFFF738) and return; count >= limit -> 0x010800(0x2100, 0)
     (0x2200 / 0x2300 for byte 0xFFFF0008 = 1 / other) and the endless loop 0x00FBA4 (SR.I := 15): the
     kernel never starts.  0x00FABC (0x00AE1C) zeroes IPRL just before 0x003324, closing the window.  So at
     the kernel start 0xFFFF0004 = the number of ITIs taken in the window, 0..182.  How many that is depends
     on the ratio of CPU speed to the WDT clock, which the bytes do not give: NOT ESTABLISHED (pass G shows
     6..101 with model rates; pass C, acceptance off, shows 0).
