THREE GUARDED STORAGE FORMATS

  REC8   8 bytes, long-aligned (the code does 32-bit and fmov.s access at +0)
           +0  long   V     the value: raw float32 bits, or a 32-bit integer
           +4  word   CK    check word
           +6  word   CK    second copy of the same check word
         CK(V) = ~( (V >> 16) + (V & 0xFFFF) ) & 0xFFFF
         i.e. the one's complement of the 16-bit sum of the two halves of V.
         A record is VALID when CK(V) equals the word at +4 OR the word at +6.
         It is NOT a comparison of two copies of the value: there is one value and
         two copies of its 16-bit check word.

  PAIR8  2 bytes:  +0 byte b,  +1 byte ~b         valid when [+0] == ~[+1] (8 bits)
  PAIR16 4 bytes:  +0 word w,  +2 word ~w         valid when [+0] == ~[+2] (16 bits)

  CONSTANT-FILL MEMORY (emulated, all 256 fill bytes through every validator and the reader)
    REC8    8 x 0x00 and 8 x 0xFF are INVALID.  8 x 0x55 is VALID: CK(0x55555555) =
            ~(0x5555 + 0x5555) & 0xFFFF = 0x5555, which is the word at +4. It reads back as
            the value 0x55555555 (as a float: 1.4660155e13). 0x55 is the only constant fill
            that validates. So "blank memory is invalid" holds for 0x00 and 0xFF, not in general.
    PAIR8 / PAIR16   no constant fill validates (b == ~b is impossible).

THE INTERRUPT WINDOW (every "yes" above uses exactly this sequence)

      jsr 0x00317C  with r4 = 16 (0x10)      -> r0 = old (SR & 0xF0)
      mov r0,r4                              -> r4 = saved mask, kept until ...
      ... touch the record ...
      jsr 0x003190  with r4 = saved mask     -> SR = saved mask

  0x00317C raises the SR interrupt mask to r4 only if r4 is unsigned-greater than
  the current (SR & 0xF0); with r4 = 0x10 that means: mask level 0 becomes level 1,
  any level >= 1 is left alone. It is NOT "disable all interrupts": priority 2..15
  sources stay enabled inside the window.
  0x003190 writes SR = r4 on every exit. If r4 == 0 (the caller was running with
  everything enabled) it also reads byte @(1, long @0xFFFF12A0) and, unless that
  byte is 1, tail-jumps to 0x003664 after SR = 0.

  SR SIDE EFFECT of every "yes" row. 0x003190 loads the WHOLE of SR, and what it is
  given is (old SR & 0xF0) (003180). So each masked helper returns with the I field
  as it found it and with M, Q, S and T all 0, whatever they were on entry -- at any
  entry mask (emulated, section 9). The NaN exit of 0x0BDBCC, the two unmasked
  writers and the six leaves load nothing into SR. In this ROM that is inert: no
  reached instruction is `sets`, `clrs`, `mac.l` or `mac.w` (scan of the 286,090
  reached instructions), M and Q are set afresh by div0s/div0u, and T does not
  survive any call.

  WHAT THE WINDOW COVERS. Entered at mask 0, the record is touched at I = 1 and
  nowhere else (emulated: every access logged with the I field at that instant).
  0x0BDB30 looks at the value TWICE inside one window (two word reads for the check,
  then a separate long read for the result); the two validators read it once.

  THE MASK-0 EXIT. A helper entered at mask 0 leaves through 0x003190's r4 == 0 path.
  If the byte is not 1 that is 0x003664, which may save the running context
  (0x003440) and hand the CPU to the scheduler; the helper's last instructions then
  run only when the context is resumed. By then its work on the record is complete
  (emulated, section 8). What survives such a switch is r8-r14, gbr, mach, macl, pr,
  SR, and fr12-fr15 only when a byte in the record at long @0xFFFF12A0 is 4 -- NOT
  r0-r7, fr0-fr11 or fpul. No helper RESULT depends on those: every result is
  rebuilt from r14 / fr14 / an immediate after the call to 0x003190.

    CK(V) = ~((V >> 16) + (V & 0xFFFF)) & 0xFFFF.  Computed at 0BDB42-0BDB4E, 0BDBA2-0BDBA8,
    0BDBE2-0BDBE8, 0BDC80-0BDC8C, 0BDCCC-0BDCD8; stored at 0BDBB4/0BDBBC and 0BDBF4/0BDBFC.
 2. Validity rule is "CK(V) == [+4] OR CK(V) == [+6]" (0BDB50-0BDB5A, 0BDC8E-0BDC98,
    0BDCDA-0BDCE4). It is a one's-complement sum check with a duplicated check word, not a
    two-copy compare of the value, not a complement-of-value check, and not a range check.
    Of the 256 constant fills only 0x55 validates (as the value 0x55555555); 0x00 and 0xFF do
    not. No constant fill validates as a PAIR8 / PAIR16. Emulated (sections 3, 4, 5).
 3. 0x0BDBCC is a float WRITE: (r4 = record, fr4 = value) -> r0 = 0; NaN -> r0 = 1 and no
    write, no mask change (0BDBDA-0BDBDE, 0BDC00). Emulated.
 4. 0x0BDCB6 is a float-record VALIDATE: r0 = 0 valid / 1 invalid; on valid both check words are
    rewritten (0BDCEA-0BDCEE); on invalid nothing is written; the value is never returned in
    r0/fr0. It has no NaN test (no fcmp in 0BDCB6..0BDD00). fr8 is loaded with the record's
    float at 0BDCC8 and still holds it on return ONLY when no context switch happens inside
    0x003190 / 0x003664; see 9. Emulated.
 5. 0x0BDB92 / 0x0BDC6A are the integer twins of 3 / 4; 0x0BDB92 has no NaN test and always
    returns 0. Emulated.
 6. 0x0BDB30 is the only function here that RETURNS a stored value: fr0 = float if valid, else the
    caller's fr4. It never writes the record. It reads the value twice (0BDB42/0BDB44 for the
    check, 0BDB5C for the result); the validators read it once (0BDC7C, 0BDCC8). Emulated with
    the access order logged.
 7. 0x0BDB6E / 0x0BDC0E: byte + complement pair, write (unmasked, r0 = 0) and validate
    (masked, r0 = 0/1). 0x0BDB80 / 0x0BDC3C: the same for a word. Emulated.
 8. Write order in 0x0BDBCC and 0x0BDB92 is +4, value, +6, with the +6 store in the delay slot of
    the jsr to 0x003190 (0BDBF4, 0BDBF6, 0BDBFC; 0BDBB4, 0BDBB6, 0BDBBC). Starting from a record
    whose +6 word is good, each of the four states the record passes through validates and reads
    as either the complete old value or the complete new value. If the +6 word was ALREADY bad,
    the first intermediate state (old value, new +4 word) is valid exactly when CK(new) == CK(old)
    -- then it reads as the old value -- and invalid otherwise; the two later states are valid as
    the new value regardless. Emulated (section 7: 6 pairs with equal check words, 304 without).
 9. Interrupt handling. 0x00317C(0x10) raises the SR mask from level 0 to level 1 and otherwise
    leaves it (003182-003188); 0x003190 loads SR with the saved (old SR & 0xF0) on every exit
    (0031A2, 0031A6), so every masked helper returns with I as found and M = Q = S = T = 0. With a
    saved mask of 0 and byte @(1, long @0xFFFF12A0) != 1 it tail-jumps to 0x003664 (0031A0),
    which returns r0 = 0 either at once (word @0xFFFF128C == word @0xFFFF128E, or bit 0x1000 of
    long @0xFFFF1290 set: 003678-003682, 0036A4) or after saving the context through 0x003440
    (00369C). 0x003440 saves SR, pr, r8-r14, gbr, mach, macl and, only when byte @(0,r6) == 4,
    fr12-fr15 (003440-00346A); the resume routine 0x00379C reloads exactly that
    (0037CE-0037EC). r0-r7, fr0-fr11 and fpul do not survive that path. All of it executed
    natively with a modelled SR, except the scheduler from 0x0034B4 on and the resume routines,
    which are bytes only.
    0x0BDB6E, 0x0BDB80 and the six integer leaves do not touch SR's I, M, Q or S at all.
    No reached instruction in the ROM is sets, clrs, mac.l or mac.w.
10. 0x0BDD0C = u16 saturating subtract (uncalled). 0x0BDD1C = u16 weighted mean
    a +/- ((|b-a| * (0x10000-k)) >> 16), k == 0 -> b. 0x0BDD5A = signed clamp (x, hi, lo).
    0x0BDD6E = unsigned 32-bit min. 0x0BDD78 = max by low 16 bits, whole register returned.
    0x0BDD88 = signed absolute difference. All emulated against a Python reference.
11. No function in 0x0BDB30..0x0BDD9B reads a table descriptor, an axis, calibration ROM or a
    peripheral register. The only literal pool (0x0BDD04, 0x0BDD08) holds two code addresses.
12. Bytes of 0x0BDB30..0x0BDD9B, 0x00317C..0x0031AF, 0x003440..0x003477, 0x0034B4..0x0034CB,
    0x003664..0x0036C3, 0x00379C..0x00381F and the table 0x004090..0x00409F are identical in
    rom/ae5l600l.bin and in the 20.19c reference, so everything above holds for both.
13. Call sites, whole ROM (scan section): 0x0BDBCC 367 (330 jsr + 37 jmp) in 166 functions;
    0x0BDCB6 129 jsr in 63 functions; 0x0BDB92 39; 0x0BDC6A 10; 0x0BDB30 3; 0x0BDB6E 5;
    0x0BDB80 5; 0x0BDC0E 2; 0x0BDC3C 2. Ten of the 0x0BDCB6 sites and one 0x0BDBCC site call
    through a stack-spilled copy of the pointer (0754AC/075564 -> 0754BC.., 01E488 -> 01E5F8).
    Where r4 is a constant, 0x0BDBCC is given 122 distinct long-aligned RAM addresses in
    0xFFFF2050..0xFFFF85FC and 0x0BDCB6 the same 122; 0x0BDB92 and 0x0BDC6A share the same 10
    (0xFFFF3C70..0xFFFF3CE8). No address is in both families.
14. Use of r0 by callers. After 0x0BDCB6 (129 of 129), 0x0BDC6A (10 of 10), 0x0BDC0E and
    0x0BDC3C (2 of 2 each) the instruction at the return address is exts.b r0,Rn followed by
    tst. After 0x0BDBCC r0 is read at none of the 330 jsr sites, nor at any of the 168 further
    call sites of the 127 functions that can (by an over-approximating rule) pass its r0 upward,
    including the table-dispatched 0x00E55C and its dispatcher 0x00FDB4 (00E572, 00FDD0..00FDE8):
    the NaN refusal is never read on any statically known path.
15. Function 0x0BCD46, when its byte argument is 0, validates record 0xFFFF85DC (0BCD68) and, if
    the verdict is non-zero, rewrites it with the float read from 0xFFFF85B8 before the
    validation call (0BCD6A, 0BCD76); on the same branch it then stores a newly computed float
    to the record whatever the verdict was (0BCE12). With a non-zero argument none of the
    three calls runs (0BCD5A/0BCD5C, 0BCDFC/0BCDFE).
16. FPSCR: the only literal loads are 0x00040001 (00FA44) and 0x00000000 (05873E); the six other
    writers are stack pops. Bits 11..7 are 0 in both literals.
17. scripts/mapping/find_writers.py cannot see a store made through 0x0BDBCC / 0x0BDB92: it
    reports no writer for 0xFFFF3674, 0xFFFF2D38, 0xFFFF2D40 (21, 2 and 2 helper stores exist).

================================================================================
NOT ESTABLISHED
================================================================================
 1. WHAT any record holds. 122 float records and 10 long records are named above by address
    only, and at 47 call sites r4 is computed, so there may be more. Settle per record by
    decoding its writer (the caller that computes fr4) -- not from a label.
 2. WHY the records are guarded (battery-backed / learned values that must survive reset, versus
    plain cross-task shared data). The torn-write property in ESTABLISHED 8 is consistent with
    reset tolerance but does not prove intent. Settle by decoding the reset path: is
    0xFFFF2000..0xFFFF3FFF cleared at start-up, and do the callers that test 0x0BDCB6 run from init?
 3. What the level-1 mask protects against. Only priority-1 interrupt sources are held off, and
    0x0BDB30 looks at the value twice inside that window. Whether any interrupt of priority >= 2
    writes a guarded record was not examined. Settle from the IPRx set-up and the vector table.
 4. What word @0xFFFF128C, word @0xFFFF128E, bit 0x1000 of long @0xFFFF1290 and the record at
    long @0xFFFF12A0 ARE (running task / ready task / lock is the obvious reading and is not
    proved here), which resume routine the dispatcher selects for a frame saved by 0x003440,
    and what runs in between. Bytes were read for 0x0034B4..0x0034C2 and 0x00363E..0x00364E
    only. Settle by tracing 0x0034CC / 0x0035FC (disassembly/analysis/rtos_core_trace.txt covers
    that ground; it was not used as evidence here).
 5. Whether a NaN ever reaches 0x0BDBCC at run time. If one does, the store is skipped and
    nothing in the ROM notices (ESTABLISHED 14). The follow-up covers every statically resolved
    call, tail-jump and bra tail-call, plus the one table dispatch the chain meets (0x00FDB4).
    It ends at six vector-table entries and at 0x010F4C, which nothing in the image references;
    whoever reaches 0x010F4C (if anything does) is outside the follow-up. A pointer built at run
    time would escape it too (none was seen).
 6. The size of the record population. 122 + 10 are the addresses that are constants at a call
    site. The scan's assumptions (callee preserves r8-r15 and the caller's frame) are the
    calling convention, not a proof per callee.
 7. Behaviour of 0x0BDBCC for a signalling NaN or a denormal on silicon. The emulator gives T=0
    for every NaN and flushes denormals to zero for the compare. No instruction loads FPSCR
    with an exception-enable bit (ESTABLISHED 16), PROVIDED each of the six stack pops takes
    back what an sts.l fpscr pushed -- the pairing was read, not walked. That an fcmp/eq on a
    signalling NaN cannot trap with the enable clear is the hardware manual's statement, not
    something these bytes show.
 8. How 0x0BDD0C is reached, if at all (no reference found). And everything about 0x0BDD9C
    beyond the entry signature above.
 9. In 0x0BDD1C, which operand is the previous output and which the new sample (caller matter).
10. Whether 0xFFFF3674, 0xFFFF2D38 and 0xFFFF2D40 are timers (comparison A11b). Settle
    0xFFFF3674 by decoding 0x00C8E8 and the u16 at 0xFFFF8EE0; the pair by decoding what fn
    0x07515E / 0x0752D4 store into the other eight records of the run.
