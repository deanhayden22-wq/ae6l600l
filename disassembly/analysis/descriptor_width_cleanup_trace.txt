FIX 1 DIFF REPORT - what actually changed, and one thing that did NOT
--------------------------------------------------------------------------------
*** IMPORTANT CORRECTION TO THE BRIEF'S PREMISE ***
The brief says the three trace_*.py scripts "generated avcs_analysis.txt,
boost_control_analysis.txt and map_switching_analysis.txt". They do not. Each
writes the corresponding **_raw.txt**; the *_analysis.txt files are hand-authored
prose derived from them. So the regeneration touches the raw files only.

And a wholesale regeneration would have been a NET LOSS. Diffing the freshly
generated raw files against the committed ones:

  avcs_raw.txt          27 dtype corrections  BUT  2 instructions downgraded
                                                    (0x031E7E `425A lds r2,fpul`
                                                     -> `.word 0x425A`)
  map_switching_raw.txt  5 dtype corrections  BUT 18 instructions downgraded
                                                    (0x04005A etc. `4F13
                                                     stc.l gbr,@-r15` -> `.word`)
  boost_control_raw.txt  9 dtype corrections, no regressions

The committed raw files contain manual disassembly improvements the scripts
cannot reproduce -- their built-in decoders do not know `lds Rm,FPUL` or
`stc.l GBR,@-Rn`. This is exactly CLAUDE.md's warning that the per-script
decoders in scripts/disasm/ are "usable, not authoritative".

**Therefore the raw files were NOT overwritten.** They were reverted to HEAD and
then patched surgically: only the type claim on each descriptor line was
rewritten, with truth read from the ROM typecode byte per descriptor address
(and, in avcs_raw.txt, from the `+0x10:` raw-bytes line already printed above
each `Parsed as 2D` line). Result, line-for-line with zero collateral change:

  avcs_raw.txt          27 changed / 27 lines touched
  boost_control_raw.txt  9 changed /  9 lines touched
  map_switching_raw.txt  5 changed /  5 lines touched

D1 - 0xFFFF4130: THE BRIEF'S INFERENCE WAS WRONG. It is BATTERY VOLTAGE.
--------------------------------------------------------------------------------
The brief INFERRED baro, and correctly named its weakest link ("I have not
traced the writer"). The weakest link broke.

Writer, routine ending 0x005A5E:
  005A40  C70C  mova @(0x005A74),r0    ; [0x5A74] = 0x47800000 = 65536.0
  005A46  F32D  float fpul,fr3
  005A48  F323  fdiv fr2,fr3           ; fr3 = filtered / 65536.0
  005A4C  D30A  mov.l @(0x005A78),r3   ; [0x5A78] -> 0x0C0098, value 20.0
  005A52  F312  fmul fr1,fr3           ; fr3 = (filtered/65536) * 20.0
  005A56  F23A  fmov.s fr3,@r2         ; [0xFFFF4130] = fr3      <-- WRITER

Full scale is **0..20**. That is volts. Barometric pressure would scale to
~15 psi or ~101 kPa or ~1 bar, not 20.

This independently confirms docs/corrections.md **item 10**, which had already
settled 0xFFFF4130 = battery voltage by the strongest method available here:
it feeds the definition-named axis 0xD91CC "Ignition Dwell / Battery Volts"
with breakpoints 8, 10, 12, 14, 16 V.

So the artifact that is wrong is **adc_pipeline_trace.txt**, not corrections.md.
Its ADDR-4 pipeline STRUCTURE (raw 0xFFFF402C -> filt 0xFFFF4134 -> out
0xFFFF4130) is correct and is corroborated by the writer above; only the sensor
NAME attached to ADDR 4 was wrong.

Knock-on: adc_pipeline_trace.txt also claimed ADDR 7 (out = 0xFFFF41E0) is
battery voltage. It is not, and item 10 had already rejected that. Traced here:

  00815C  D313  mov.l @(0x0081AC),r3   ; -> 0x0C00B4 = -62.5

D3 - the dispatch trampolines (VERIFIED), and func_3952C's caller (FOUND)
--------------------------------------------------------------------------------
Both tables decoded from the bin. Trampoline = the slot address is a `bra`.

  table A @ 0x0480B8, 19 entries -- ONE trampoline:
    A[13] 0x03756C -> 0x03757E
  table B @ 0x04A0B8, 20 entries -- SIX trampolines:
    B[ 5] 0x03160A -> 0x03161E      B[ 8] 0x039528 -> 0x039668
    B[10] 0x036C3C -> 0x036C48      B[11] 0x037B68 -> 0x037B74
    B[15] 0x03605E -> 0x03643A      B[17] 0x03A222 -> 0x03A230

Matches the brief exactly. The entry addresses in fueling_pipeline_analysis.txt
are right; the functions behind seven of them start elsewhere.

**B[8] dispatches to 0x039668, and nothing in either table reaches func_3952C.**
Confirms the brief's sharp case.

**func_3952C's caller: FOUND.** There is a THIRD dispatch table, 93 contiguous
code pointers at **0x04ACB8-0x04AE28**. Slot 20 (`0x04AD08`) holds
**0x00039524** -- the stub whose `bra` lands on 0x03952C.

  0x00039524 occurs exactly once in the whole ROM, at 0x04AD08.
  0x00039528 occurs exactly once, at 0x04A0D8 = table B base + 4*8. (B[8].)
  0x0003952C and 0x00039668 occur nowhere.

So the 0x39524 / 0x39528 stub pair is not an off-by-one at all: the two stubs
are entries in two DIFFERENT tables. Table B slot 8 reaches 0x39668 via 0x39528;
table C slot 20 reaches func_3952C via 0x39524.

OPEN: no 4-aligned literal anywhere points at 0x04ACB8 or 0x04ACB4, so the
consumer of table C is not yet located. It is presumably reached with a
non-zero displacement or a computed base. NOT chased.

    0x37B68  A004 -> 0x37B74
    0x37B6C  A071 -> 0x37C52
    0x37B70  A096 -> 0x37CA0
and 0x37B70 is itself slot 29 of table C (0x04AD2C = 0x00037B70). So this is a
stub group with three distinct entry points, and "0x37B68 and 0x37B74 are one
function" is true only for that pair.

func_37B74, VERIFIED from its preamble:
    GBR = 0xFFFF7AB4                       (literal 0x037CEC)
    r13 = 0xFFFF7AD8                       (literal 0x037D24)
    fr8 = float[0xFFFF6624]  = RPM         -> stored at [r13-4] = 0xFFFF7AD4
    fr8 = float[0xFFFF6350]  = ECT         -> stored at [r13]   = 0xFFFF7AD8
    byte[0xFFFF726C] -> @(28,gbr) ; byte[0xFFFF7C68] -> @(30,gbr)
    two table_lookup (0xBE830) calls on descriptors 0x0AC648 and 0x0AC634

Both descriptors decoded from the bin:
    0x0AC634  1D, 16, uint8, scale 1/128, bias 0
              axis 0x0CCE18 = 0,800,1200,...,6400   (RPM)
              data 0x0CCE58 = ALL ZERO
    0x0AC648  1D, 16, uint8, scale 1/128, bias 0
              axis 0x0CC624 = -40..110              (ECT)
              data 0x0CCE68 = ALL ZERO

So: the inputs are **RPM and ECT**, the tables are **1-D**, and both are

fueling_pipeline_analysis.txt:61 calls B[11] "Injector compensation (2D maps,

**Neither existing name is supported by what was decoded. I am not inventing a
