ITEM 8 — 0xAE284 IS NOT AN "RPM x IAT KNOCK THRESHOLD". IT IS A 1-D KNOCK-SIGNAL CURVE.
--------------------------------------------------------------------------------
Project notes recorded 0xAE284 as the knock detection threshold, RPM x IAT,
"no mrp/load input". Decoded from the bytes, all three parts are wrong.

The descriptor:
  0AE284  1D, 65 points, float32, axis 0x0D4128 = 0.0 .. 3.5 (monotonic),
          data 0x0D422C = 0.0 .. 304.0
(It read `invalid` in desc_func_xref.txt until item 43's off-by-one was fixed,
and until the size guard was raised past 64 — which is why nobody had decoded it.)

Its ONE consumer is the knock detector at 0x043798 (GBR=FFFF80FC — the same
function that writes KNOCK_FLAG). The input is NOT rpm, load or IAT:

  0437A8  D283  mov.l @(0x0439B8),r2   ; 0x0439B8 = 0xFFFF4304
  0437AA  F828  fmov.s @r2,fr8         ; fr8 = knock signal level
  0437AC  FC8D  fldi0 fr12
  0437AE  FC85  fcmp/gt fr8,fr12       ; clamp at zero
  0437B0  8B00  bf 0x0437B4
  0437B2  F8CC  fmov fr12,fr8
  0437B4  D981  mov.l @(0x0439BC),r9   ; 0xFFFF8158
  0437B8  F987  fmov.s fr8,@(r0,r9)    ; [0xFFFF8134] = clamped signal
  0437BA  D481  mov.l @(0x0439C0),r4   ; r4 = 0x000AE284  (descriptor)
  0437BC  DC81  mov.l @(0x0439C4),r12  ; r12 = 0x000BE830 (table_lookup)
  0437BE  4C0B  jsr  @r12
  0437C0  F496  fmov.s @(r0,r9),fr4    ; delay: fr4 = the clamped signal

So 0xAE284 maps **knock signal level (0..3.5) -> 0..304**. A transfer curve on
the sensor, not a threshold on RPM/IAT.

AND the "no load input" claim is contradicted separately: the knock module DOES
contain 2-D **RPM x LOAD** tables, decoded from the bytes —
  0AE5D8  14x5 uint8   Y = 1200,1600,2000,2400,2800,3200,3600,4000...
                       X = 0.5, 0.8, 1.4, 1.8, 2.2      <- LOAD
  0AE5F4  14x5 uint8   same axes
  0AE610  14x5 uint8   same axes
  0AE62C  14x6 uint8   X = 0.5, 0.8, 1.0, 1.3, 1.8, 2.3 <- LOAD
consumed at 0x0441C0-0x0441F0 (a different routine in knock_area, not the
detector). The detector itself reads RPM (0xFFFF6624 -> FR15) and engine load
(0xFFFF63F8 -> FR14) in its preamble at 0x04379C/0x0437A0.

STATED LIMIT: I did NOT establish that the 14x5 tables ARE the detection
threshold. What is settled is narrower and sufficient to retire the old claim:
0xAE284 is not it, it is not 2-D, and it is not RPM x IAT. The blanket "knock
detection has no load input" should be treated as UNVERIFIED, not inverted.

ITEM 13 — THE FLKC TRAVERSAL TEST. THE ORIGINAL READING WAS BACKWARDS.
--------------------------------------------------------------------------------
New tool `scripts/analysis/flkc_cell_trace.py` replicates the ECU band selector
exactly (boundaries + downward-only hysteresis, 50 rpm / 0.02 load) and computes
cell = rpm_band*5 + load_band per sample, then classifies every FLKC change.

Run against logs/8-14 weekend 20.19c (221,829 samples parsed):

    FLKC changes total : 64
      CELL TRAVERSAL   :  5   (index moved -- a different cell was read)
      IN-CELL CHANGE   : 59   (index held -- the STORED VALUE moved = LEARNING)

    in-cell step sizes: {-1.00: 3, -0.25: 29, +0.25: 23, +0.50: 2, +1.00: 2}

The shape is the textbook learn-then-recover cycle, in place:
      9564.92  3288 rpm  1.57 load  cell 18   0.00 -> -1.00
      9701.68  2952 rpm  1.57 load  cell 18   0.00 -> -0.25
      9701.84  2959      1.57       cell 18  -0.25 -> -0.50
      9702.08  2976      1.67       cell 18  -0.50 -> -0.75
      9702.12  2998      1.67       cell 18  -0.75 -> -1.00
      9702.84  3068      2.27       cell 19  -1.00 -> -0.75   (then +0.25 x3
      9703.28  3100      2.54       cell 19  -0.25 ->  0.00    back to zero)

**92% of FLKC movement on 8-14 was in-cell.** The ECU was ACTIVELY LEARNING
during that drive. The earlier conclusion — "all 33 step-downs passed the
traversal test = lookups of a pre-learned map, not in-drive learning" — is
wrong, and it was wrong because it used step SIZE (0.25) as the discriminator.
Under a bucketed map that proves nothing: 0.25 is simply the Fine Correction
Advance Value (0xD2F48), so an in-place ramp and a traversal look identical by
step size. Only the cell index separates them.

CAVEATS, stated:
  * FLKC is logged at 0.25 resolution (scalingrpn x,0.25,*,32,-), so sub-step
    movement is invisible and the counts are lower bounds.
  * The band index is reconstructed from the same 25 Hz rpm/load samples, so a
    fast in-and-out excursion between samples could be misclassified as in-cell.
    5 traversals out of 64 is low enough that this cannot flip the conclusion.

FINAL ANSWER ON THE LOAD QUESTION:
  * The threshold IS RPM x LOAD indexed, per cylinder, and IS populated:
    3.60 at low RPM falling to 3.45 above 5200.
  * The LOAD DIMENSION IS EXACTLY FLAT -- both planes identical, so load moves
    the threshold by zero.
  * "No load input" was right about the effect and wrong about the mechanism;
    item 56's "zeroed" explanation was ALSO wrong. The tables are populated, the
    load AXIS is degenerate.
